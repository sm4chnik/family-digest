# План разработки

Документ описывает этапы реализации. Код появится после согласования/фиксации документации.

## Принципы

- Сначала вертикальный срез: один пользователь → сдал фото → пост в канал.
- Потом расписание, DND, soft-ping, админ-интервал.
- Маленькие PR/коммиты по этапам ниже.
- Спека ([SPEC.md](./SPEC.md)) — источник правды по поведению; при расхождении обновляем спеку явно.

## Этап 0 — Каркас репозитория

- TypeScript + Cloudflare Workers проект (`wrangler`)
- ESLint/Prettier по минимуму (или без лишней бюрократии)
- Структура папок: `src/bot`, `src/rounds`, `src/db`, `src/telegram`
- D1 schema + миграции
- `.env.example` / описание secrets
- Локальный `wrangler dev` + туннель для webhook (cloudflared или аналог)

**Критерий готовности:** Worker отвечает на health/ping, миграции применяются.

## Этап 1 — Telegram plumbing

- Установка webhook
- Парсинг update
- Отправка сообщений (text, photo, video, video_note) в чат и канал
- Проверка, что бот — админ канала с правом постить

**Критерий:** вручную командой админа «тест пост» появляется в канале.

## Этап 2 — Онбординг и настройки

- `/start` + сохранение пользователя в D1
- Выбор timezone
- Опциональный DND + валидация ≤ 12 часов
- Меню изменения TZ / DND
- Хелпер `isInDnd(user, nowUtc)`

**Критерий:** пользователь проходит онбординг, настройки читаются из БД.

## Этап 3 — Приём медиа и публикация вручную

- Ingest photo/video/video_note → `submissions`
- Временная админ-команда «опубликовать очередь» (до появления раундов)
- Подпись `от {display_name}`

**Критерий:** медиа из лички оказывается в канале с правильной подписью.

## Этап 4 — Раунды

- Таблицы `rounds`, статусы
- Старт раунда по интервалу (cron tick)
- Напоминание всем вне DND
- Окно 30 минут: приём в текущий раунд vs late → следующий
- Soft-ping на 20-й минуте
- Авто-публикация по закрытию окна
- Идемпотентность (не слать пинг дважды, не публиковать дважды)

**Критерий:** полный цикл без ручных команд админа.

## Этап 5 — Админка

- Смена `round_interval_hours`
- Статус: текущий раунд, next run, число участников
- (Опционально) список «кто не сдал в открытом окне» только для админа

**Критерий:** админ меняет интервал на 3 часа, следующий цикл это учитывает.

## Этап 6 — Полировка UX

- Тексты напоминаний и пингов
- Понятные ответы на «просто текст» / стикеры («пришли фото, видео или кружок»)
- Справка `/help`
- Обработка краевых случаев: удалил канал, бот потерял права, пустой дайджест (не постить ничего / тихий skip)

**Критерий:** можно отдавать семье без сопровождения разработчика.

## Этап 7 — Деплой и чеклист семьи

- Prod Worker + D1 + secrets
- Webhook на prod URL
- Инвайт-инструкция для родственников (короткий MD или сообщение)
- Смоук-тест на 2–3 участниках

См. [DEPLOY.md](./DEPLOY.md).

## Технические решения (каркас)

1. **Библиотека:** тонкий fetch-клиент в `src/telegram/api.ts` (без grammy/telegraf) — меньше веса на Workers; расширяем по мере надобности.
2. **Late queue:** `target_round_id = NULL` у submission = очередь на следующий раунд; при старте раунда NULL-записи привязываются к новому `rounds.id`.
3. **Video notes:** в канал шлём `sendVideoNote`; имя автора — отдельным коротким сообщением сразу после (API не даёт caption у video note). Уточним в этапе 3 при полировке.
4. **Имена:** `first_name` + `last_name`, иначе `username`, иначе numeric id (`displayNameFromUser`).
